# 이미지피드 — 16차 작업 결과와 17차 인계 (2026-10-28)

저장소: https://github.com/Joonwang-Ji/imagefeed (main). 변경 파일을 ZIP(imagefeed-round16.zip)으로 전달 → GitHub 웹에서 같은 경로로 덮어쓰기 업로드(자동 배포). 새 파일: `public/vendor/nsfw4/*`(4개), `public/_headers`, `tools/nsfw-entry.js`, `tools/build-nsfw.sh`, `tests/vendor.test.mjs`, `docs/handoff-round16.md`.
키: Pixabay, Unsplash, 카카오, 네이버 등록됨. 원칙(바꾸지 말 것): 검색·조회 기록 저장 금지, 공포·잔혹 해제 불가, 선정성 기본 블러(설정에서 해제), 사용자는 본인과 소수 지인(성인), 기독교 세계관.

## 배경 (15차 이후 사용자 질문)
1. 비공개로 검색한 연예인 사진이 '아무거나'(안개 속 빛) 피드에 섞임 → 코드 점검 결과 비공개 모드는 취향 학습·반영 경로를 모두 막고 있음(`tasteOn() = S.taste && !S.priv`). '아무거나'는 고정 목록(`CATS`)에서 무작위 선택. 가장 유력한 원인은 외부 검색 결과 자체(한 화보 세트가 여러 장 나옴). 확정 아님(실기기 확인 대기: 앱 완전 종료 후 재검색, 다른 주제에서도 나오는지, 사진의 제목·출처).
2. 첫 검색 때 카드는 뜨는데 스피너가 오래 돎 → 브라우저 AI 선정성 검사(`data-st=pending`) 대기. 모델은 첫 이미지 검사 때 `idle(4000)` 대기 + 외부(esm.sh)에서 라이브러리·모델 내려받기 + 초기화(5초 안팎). 앱을 켤 때마다 다시 초기화.

## 16차에서 바뀐 것 (3번: 모델·라이브러리를 앱 안에 두기)
- `public/vendor/nsfw4/` : nsfwjs 4.x 의 **MobileNetV2 기본 모델만** esbuild 로 묶은 번들(nsfw.js 1.1MB + 가중치 3.5MB + 모델 정의 0.1MB, gzip 약 2.8MB). 다른 모델(InceptionV3 등)은 제외. 모델 가중치는 4.3.0/4.4.0 이 바이트 단위로 동일(해시 확인), 4.4.0은 classify 의 topK 보정만 다름 → 기존(esm.sh) 점수와 동일하게 동작.
- `public/app.js` `getModel()` : `import("/vendor/nsfw4/nsfw.js")` 를 먼저, 실패하면 예전 esm.sh 로 대체.
- `public/_headers` : 번들에 `Cache-Control: public, max-age=31536000, immutable`.
- `public/sw.js` v15 : 번들은 별도 캐시(`imagefeed-vendor-nsfw4`)에 cache-first, 버전을 올려도 이 캐시는 지우지 않음.
- `tools/build-nsfw.sh` : 번들 재생성 스크립트(평소 실행 불필요).
- 그대로 둔 것: `idle(4000)` 대기(첫 이미지 검사 때 브라우저가 한가할 때까지 최대 4초), 접속 직후 미리 받기. → 아직 체감 지연이 남으면 다음 후보 1·2.

## 검증
- 기존 자동 점검 10개 파일 + 새 `tests/vendor.test.mjs`(번들 조각 파일 존재, 앱·서비스워커·헤더 연결, 외부 주소가 예비로만 남았는지) 통과. app.js 를 예전 방식으로 되돌리면 vendor 테스트가 실패함을 확인.
- **실제 Chromium(Playwright)에서 번들을 불러와 모델 로드·classify 성공**(합성 이미지 한 장: Neutral 0.95). 이 환경 수치(로드 1.9초, 첫 classify 1.6초)는 GPU 없는 소프트웨어 렌더링 기준이라 실제 아이폰과 다름. esm.sh 는 이 환경에서 접속이 막혀 두 버전의 점수를 직접 비교하지는 못함(모델 파일 해시 동일로 대신 확인).
- **실기기 미확인**: 아이폰 Safari·홈 화면 앱에서 첫 검색의 스피너 시간, 두 번째 앱 실행 때 캐시 효과, 비행기 모드에서의 동작(번들이 서비스워커 캐시에 들어간 뒤).

## 배포 후 확인할 것
1. 앱을 완전히 종료했다가 열어 첫 검색: 스피너가 도는 시간이 이전보다 줄었는지. 두 번째 실행(번들이 캐시된 뒤)은 더 빨라야 함.
2. 설정 화면의 AI 검사 상태(준비됨/실패)가 정상인지. 실패로 나오면 브라우저 개발자 도구 없이도 확인할 수 있게 알려 주기 → 예비 경로(esm.sh)로 넘어갔는지 판단.
3. 연예인 사진 섞임 재확인(위 배경 1).

## 취향 학습 새 접근 — 설계안 (구현 전, 결정 대기)
문제: 지금은 취향 = **단어별 점수**이고, 홈 추천은 상위 단어를 **하나씩 따로 검색**해 섞음 → 단어를 나열한 느낌이고 서로 다른 관심사의 "패턴"이 안 보임.

핀터레스트의 공개 자료에서 가져올 구조(출처 아래):
- 핀(이미지) 하나를 **벡터(임베딩)** 로 표현: 이미지 모양 + 텍스트 + "사람들이 같은 보드에 같이 저장한 정도"(PinSage).
- 사용자 = 벡터 하나가 아니라 **여러 개의 관심사 묶음**(PinnerSage): 최근 90일 저장·클릭을 군집화(Ward) → 군집마다 **대표 이미지(medoid, 실제 핀 하나)** → 군집 중요도 = 시간 감쇠 가중 합(λ=0.01/일), 동작 직후 20개는 별도로 즉시 반영, 서빙 때는 중요도 비례로 **최대 3개 관심사**를 뽑아 각각 이웃 검색 → 결과를 **돌아가며(round-robin) 섞기**.
- 앱을 열자마자 보이는 건 이 "관심사 대표 이미지 → 비슷한 이미지" 검색의 결과.

이미지피드에 맞춘 적용(자체 이미지 풀·벡터 검색이 없고 외부 API 를 검색하는 구조라는 차이 때문에 일부만 가능):
- **A단계(새 모델 없이)**: 취향의 단위를 단어가 아니라 **이미지**로. 입력은 북마크·👍(명시적 신호). 보드가 있으면 보드를 군집의 출발점으로 사용(PinSage가 쓰는 "같은 보드" 신호와 같은 것). 군집 = 태그 겹침 + 색·톤 유사도, 군집별 대표 이미지 1장. 홈 맨 위 "당신을 위한 피드" = 중요도 비례로 관심사 최대 3개를 뽑아, 각 대표 이미지로 **기존 '비슷한 이미지' 파이프라인**(태그→AI 설명→제목, 색 재정렬)을 돌려 라운드 로빈으로 섞음. 새 이미지·트렌드를 20~30% 섞어 한 쪽으로 쏠리지 않게. [🔀]로 관심사를 다시 뽑기. 데이터가 5개 미만이면 지금 방식 유지.
- **B단계(품질)**: 저장 시 (제목+태그+AI 설명)을 Workers AI 다국어 텍스트 임베딩으로 벡터화해 기기에 저장(한글·영어 모두), 군집·후보 재정렬을 코사인 유사도로. (모델 이름·무료 사용량은 실제 확인 필요)
- **C단계(선택, 비권장)**: 브라우저에서 CLIP 등 이미지 임베딩. 모델이 수십 MB 이상이라 아이폰에서 무거움.
- **개인정보 제약**: "조회 기록 저장 금지" 원칙 때문에 군집 입력은 명시적 신호(북마크·👍)로 한정하는 안을 권장. 7초 시청은 지금처럼 단어·색 **집계 점수로만** 반영(이미지 목록은 저장하지 않음). 비공개 모드에서는 학습·반영 모두 중지(현행 유지). 모든 데이터는 기기 안에만 저장.
- 한계: 외부 검색 API 로 가져오므로 핀터레스트처럼 "벡터로 이웃을 직접 찾는" 정확도는 안 나옴. B단계의 재정렬이 품질을 좌우. Unsplash 무료 한도(시간당 50회)가 있어 홈 진입 때 호출 수를 제한하고 결과는 세션 안에서만 캐시.

출처: PinnerSage(arXiv 2007.03634), PinSage(Pinterest Engineering 블로그·KDD 2018), Pinterest 홈피드 임베딩 검색(Pinterest Engineering 글을 요약한 ZenML 정리).
