# 이미지피드 — 7차 작업 결과와 8차 인계 (2026-10-27)

저장소: https://github.com/Joonwang-Ji/imagefeed (main). 변경 파일을 ZIP(imagefeed-round7.zip)으로 전달 → 사용자가 GitHub 웹에서 같은 경로로 덮어쓰기 업로드(새 파일 `public/relevance.js`, `tests/feed.test.mjs`, `tests/relevance.test.mjs`, `docs/handoff-round7.md` 포함).
키: Pixabay, Unsplash, 카카오, 네이버 등록됨. 원칙(바꾸지 말 것): 검색·조회 기록 저장 금지, 공포·잔혹 해제 불가, 선정성은 기본 블러+설정에서 해제 가능, 사용자는 본인과 소수 지인(성인).

## 신고 내용 (6차 사용 후기)
- 검색어와 상관없는 이미지가 상단에 올라옴. 예: '금강엑슬루타워' → "금강" 때문에 강·자연 사진이 먼저 뜸. 한글이 아닌 검색어에서도 자주 그럼.
- 무제한 피드보다 어느 정도 내린 뒤 [더 보기] 버튼을 넣자는 제안.
- 사용자 결정: 약한 결과는 **삭제가 아니라 맨 아래로 접어서** 보여 주는 방식(추천안) + [더 보기] 버튼.

## 원인 (코드 기준)
1. 화면의 `Feed.merge` 가 소스가 준 순위(`w/(60+i)`)만 합산 → 소스가 억지로 채운 엉뚱한 1위도 진짜 일치하는 1위와 같은 점수.
2. 번역(m2m100)이 고유명사를 뜻풀이("금강"=강) → 영어 소스가 강 사진을 반환.
3. 모든 소스를 같은 비중으로 섞음(미술관·NASA 결과가 일반 검색어에도 섞임).

## 7차에서 바뀐 것
- **관련도 점수** (`public/relevance.js`, 화면·테스트 공용 순수 함수): 제목·태그가 검색어(원문·영어 번역 중 더 잘 맞는 쪽)와 얼마나 맞는지 0~1 → 등급 strong(×2) / medium(×1) / unknown(×0.9, 제목·태그 없음 또는 글자 종류가 달라 비교 불가) / trust(×0.6, 네이버·카카오가 준 것인데 제목이 안 맞음) / weak(×0.3). 한글은 띄어쓰기 무시, 긴 복합어는 두 글자 조각 부분 일치. 고유명사는 일부 단어만 맞으면(예: "금강"만) weak, 일반 검색어는 하나도 안 맞을 때만 weak. 흔한 말(타워·아파트·강·산 등)은 가중치 절반.
- **소스별 가중치 배수** (`Relevance.bias`): 미술관 3종은 미술·디자인 검색어일 때만 ×1.4(아니면 ×0.35), NASA는 우주 검색어일 때만 ×1.4(아니면 ×0.2), 한글 검색어면 네이버·카카오 ×1.25, 고유명사면 위키 ×1.3·Pixabay/Unsplash ×0.75. 사용자가 [소스]에서 직접 고르면 배수 없음. 한 소스의 평균 관련도가 낮으면(8장 이상 판단 가능할 때) 그 소스 비중을 0.6~1배로 줄임.
- **약한 결과 접기**: 구체적인 검색어(고유명사 또는 두 단어 이상)에서 weak 는 피드에서 빼고 맨 아래 [관련도 낮은 결과 N개 보기]. 맞는 이미지가 10개 미만이면 "정확히 맞는 이미지는 N개뿐이에요"/"찾지 못했어요". 한 단어짜리 일반 검색어와 뷰어의 "비슷한 이미지"는 접지 않고 점수순만.
- **[더 보기]** (`Feed` 클래스 재작성): 받은 이미지를 대기열(`pend`)에 모아 점수순으로 한 번에 60장(뷰어 30장)만 화면에 올림. 이미 올라간 카드는 순서 불변. 첫 페이지는 600ms 뒤 12장만 먼저 보여 주고 모든 소스가 도착하면 나머지를 점수순으로 채움. 소스 순위는 쪽을 이어서 매김(`base`). 보여 줄 만한 이미지가 새로 안 나오는 쪽이 연달아 2번이거나 [더 보기] 한 번에 6쪽을 넘게 불러오면 자동 불러오기 중단(엉뚱한 결과만 나오는 검색어에서 API 폭주 방지 — Unsplash 무료는 시간당 호출이 적음). 필터·이미지 실패로 카드가 빠지면 대기열에서 자동으로 다시 채움.
- **고유명사 판별** (서버 `/api/tr`): 한글 검색어는 번역과 동시에 Workers AI 텍스트 모델(`llama-3.1-8b-instruct` → `llama-3.2-3b-instruct`, `TR_MODEL`로 지정 가능, `TR_SMART=off`로 끔)에게 `{proper, en, type}` 를 물음. 고유명사면 뜻풀이 번역 대신 로마자 영어 이름 사용, 응답 `{t, proper, type}`. 7일 캐시, 4초 제한, 실패하면 기존 번역(`proper` 없음 → 화면이 "띄어쓰기 없는 5자 이상 한글 한 덩어리"를 고유명사로 보는 자체 규칙 사용).
- **위키 저장소**: 고유명사면(`pr=1`) 영어 이름 + 한글 원문 두 번 검색해서 번갈아 섞음(한쪽이 실패해도 다른 쪽 반환).
- 서비스워커 v8(`/relevance.js` 캐시), README·wrangler 주석 갱신.

## 검증
- `tests/relevance.test.mjs`(점수·소스 가중치, '금강엑슬루타워' 사례 포함), `tests/feed.test.mjs`(순위·접기·더 보기 60장·늦게 온 소스·자동 불러오기 중단·쪽 이어 순위·뷰어 30장·홈/탭 전환), `tests/server.test.mjs`(고유명사 판별 9개, 위키 두 번 검색 5개 추가), 기존 `ui`·`color` 테스트 모두 통과.
- 일부러 기능을 되돌린 버전에서 해당 테스트가 실패함을 확인: 관련도 무시, 60장 제한 제거, 자동 중단 장치 제거, 접기 제거, 쪽 이어 순위 제거.
- 이 환경은 외부 API·Workers AI에 접속할 수 없음 → 실제 응답은 미확인. 특히 **Workers AI 텍스트 모델 이름·응답 형태(`response` 문자열 속 JSON)** 와 **Pixabay `lang=ko` 일 때 태그가 한글인지 영어인지**는 모의로만 확인(영어 태그여도 '비교 불가'로 처리되어 접히지 않게 해 둠).

## 배포 후 실제 기기에서 확인할 것
1. '금강엑슬루타워' 검색: 강·자연 사진이 상단에 안 올라오고, 아래에 [관련도 낮은 결과 N개 보기]와 안내 문구가 나오는지. 이름이 들어간 네이버·카카오 결과가 위로 오는지.
2. 일반 검색어(고양이, 바다 등): 60장 뒤에 [더 보기]가 나오는지, 누르면 이어지는지, 위로 되돌아가 보면 카드 순서가 바뀌지 않았는지.
3. 영어 검색어(예: `namsan seoul tower`): 관련 이미지가 위로 오는지, 너무 많이 접히지 않는지(접힌 개수 확인).
4. 고유명사 판별이 되는지: 한글 고유명사로 검색했을 때 위키 결과가 한글·영어 섞여 나오는지. 안 되면(응답에 proper 없음) `TR_MODEL` 로 현재 쓸 수 있는 텍스트 모델 ID 지정. Workers AI 무료 사용량 확인.
5. 미술·우주 검색어(인상주의 풍경화, 은하수)에서 미술관·NASA가 상단에 오고, 그 외 검색어에서는 안 섞이는지.
6. 첫 화면 속도(12장 먼저 → 나머지 채움), 뷰어 비슷한 이미지 30장 + [더 보기].

## 알려진 한계·조정 포인트
- 관련도는 **제목·태그 글자 비교**뿐이라 설명이 없는 사진(Unsplash 일부, 카카오)은 unknown 으로 두며, 이런 이미지는 소스 순위에 의존함. (2단계 후보: Workers AI 다국어 임베딩으로 의미 유사도 — 무료 사용량 확인 필요)
- 판단 기준 숫자(등급 배수, 고유명사 일치 0.5, 한 번에 60장, 연달아 2번 중단 등)는 `public/relevance.js`·`Feed` 상단에 있어 쉽게 조정 가능. 너무 많이 접히면 고유명사 기준 0.5 → 0.34 로 낮추기, 너무 안 접히면 올리기.
- 한 소스가 이미지를 한 장도 못 열면 다음 페이지를 안 부르는 기존 규칙(`holding`)은 그대로.
- 소스 칩의 숫자(예: 네이버 40)는 "받은 개수"이며 화면에 보이는 장수와 다름(대기열 때문).
- 색 "넓게"로 많이 걸러지는 경우: 한 번에 6쪽까지만 자동 불러오고 [더 보기]로 이어짐(이전의 최대 50쪽 자동 불러오기 제거).
